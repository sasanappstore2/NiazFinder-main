RFC-002

Universal Need Representation Model (UNRM)

Part 1 — Foundations & Conceptual Model

Status: Draft

Version: 1.0

Depends On

* RFC-000 — Vision & Principles
* RFC-001 — Human Need Grammar

⸻

1. Abstract

This RFC defines the Universal Need Representation Model (UNRM), the canonical representation used by the NiazFinder Cognitive Engine.

UNRM is not a database schema.

It is not an API contract.

It is not an AI prompt.

Instead, UNRM defines a stable conceptual model that represents every human need independently from implementation details.

Every subsystem inside NiazFinder—including AI Intake, Search, Matching, Recommendation, Analytics, and future AI Agents—communicates through this model.

UNRM acts as the single source of truth for meaning.

⸻

2. Problem Statement

Marketplace software has traditionally been built around categories.

Users are expected to classify themselves before describing their needs.

Example:

Category
↓
Subcategory
↓
Form
↓
Details

This architecture assumes users know how the marketplace is organized.

Human cognition does not work this way.

Humans begin with goals.

Examples:

ماشینم روشن نمی‌شود.

دنبال یک برنامه‌نویس React هستم.

مادرم یک پرستار شبانه‌روزی نیاز دارد.

None of these thoughts begin with categories.

Categories exist only because databases require organization.

Therefore category-first architectures introduce unnecessary cognitive load.

⸻

ADR-001

Decision

The Cognitive Engine SHALL represent meaning before classification.

Categories become a derived property rather than an input.

Rationale

Meaning is stable.

Categories evolve.

Business rules evolve.

Databases evolve.

Meaning changes far less frequently.

Therefore meaning should become the architectural foundation.

⸻

3. Vision

UNRM exists to answer a single question:

What does the user actually need?

Not

Which category should this belong to?

The second question is a consequence of the first.

Never the opposite.

⸻

4. Fundamental Observation

Human language is extremely diverse.

Human intentions are surprisingly limited.

Examples:

I need a house.
Looking for an apartment.
Need somewhere to live.
Want to rent a place.
Need accommodation.

Five completely different sentences.

One semantic intention.

⸻

Likewise:

گیربکس ماشینم خراب شده.
ماشینم دنده جا نمی‌ره.
نیاز به تعمیر گیربکس دارم.
دنبال گیربکس‌ساز هستم.

Different wording.

Same underlying need.

⸻

Therefore:

The engine must optimize for semantic equivalence rather than textual similarity.

⸻

ADR-002

Decision

Natural language SHALL NOT be stored as the primary representation.

Instead:

Natural Language
↓
Semantic Representation
↓
Canonical Need Representation
↓
Business Representation
↓
Database Representation

Natural language becomes one possible view of the need.

Not the need itself.

⸻

5. Core Philosophy

UNRM assumes every human need is composed of independent semantic components.

No component owns another.

Instead they form a semantic graph.

Example:

Need
├── Intent
├── Object
├── Location
├── Budget
├── Constraints
├── Time
├── Preferences
├── Context

Notice something important.

Location is not a child of Object.

Budget is not a child of Intent.

Time is not part of Constraints.

Everything is simply another node describing the same need.

This dramatically reduces coupling.

⸻

ADR-003

Need is a Graph

The Cognitive Engine SHALL model a need as a graph.

Not as a form.

Not as a database row.

Not as a JSON document.

JSON is only one serialization.

Internally the engine reasons over relationships.

⸻

Example

Intent
↓
Repair
↓
Object
↓
Vehicle
↓
Component
↓
Gearbox
↓
Location
↓
Mashhad
↓
Budget
↓
15M

The graph can grow without changing the model.

⸻

6. Invariants

The following properties MUST always remain true.

Invariant 1

Every Need has exactly one Primary Intent.

Secondary intents are optional.

⸻

Invariant 2

Every Need represents one publishable objective.

If multiple unrelated objectives exist,

they become multiple Needs.

Example

❌

خانه می‌خواهم
و
ماشینم را می‌فروشم.

↓

Two Needs.

Not one.

⸻

Invariant 3

A Need may contain multiple Objects.

Example

خریدار میز و صندلی هستم.

Objects

* Table
* Chair

One Need.

⸻

Invariant 4

Unknown values SHALL remain Unknown.

Never guessed.

Never synthesized.

Never hallucinated.

⸻

Invariant 5

Confidence belongs to observations.

Not to the Need itself.

Example

Location
Confidence 0.98
Budget
Confidence 0.32

Different nodes.

Different certainty.

⸻

7. Why This Matters

This model enables something that traditional marketplaces cannot do.

The same Need can simultaneously power:

* Publishing
* AI Search
* Recommendation
* Matching
* Analytics
* Business Intelligence
* Future AI Agents

without redesigning the architecture.

Meaning becomes reusable.

⸻

End of Part 1

RFC-002

Universal Need Representation Model (UNRM)

Part 2 — Evidence Model & Semantic Inference

Status: Draft

Version: 2.0

Depends On

* RFC-000 — Vision & Principles
* RFC-001 — Human Need Grammar
* RFC-002 Part 1 — Foundations & Conceptual Model

⸻

8. Motivation

Natural language is not structured knowledge.

Natural language is evidence.

Every sentence written by a user contains one or more observations about reality.

The Cognitive Engine SHALL never treat user text as truth.

Instead, it shall treat it as evidence that may support one or more interpretations.

Example

ماشینم گیربکسش خراب شده.

This sentence does not explicitly state:

* the desired service
* the marketplace category
* whether the user wants repair or replacement
* whether the user is only asking a question

It only provides evidence.

⸻

ADR-004

Decision

The Cognitive Engine SHALL extract evidence before inferring needs.

Need representation is always derived.

Never directly extracted.

⸻

Architecture

Natural Language
        │
        ▼
Evidence Extraction
        │
        ▼
Evidence Graph
        │
        ▼
Semantic Inference
        │
        ▼
Universal Need Representation
        │
        ▼
Business Objects

⸻

9. Definition of Evidence

Evidence is the smallest atomic semantic unit that can be directly justified by user input.

An evidence item SHALL satisfy the following properties:

* Atomic
* Observable
* Explainable
* Independently confidence-scored
* Traceable back to source text

Example

User

ماشینم گیربکسش خراب شده.

Extracted Evidence

E1:
  type: OBJECT
  value: Vehicle
E2:
  type: COMPONENT
  value: Gearbox
E3:
  type: STATE
  value: Broken

Notice:

No intent has been inferred.

⸻

10. Evidence Categories

Every extracted evidence belongs to exactly one category.

Identity Evidence

Defines the existence of entities.

Examples

* Vehicle
* Apartment
* Dog
* Laptop
* Company

⸻

Property Evidence

Describes an entity.

Examples

* White
* Automatic
* Two bedrooms
* 2022 model
* Male

⸻

State Evidence

Current condition.

Examples

* Broken
* Available
* Urgent
* New
* Used
* Occupied

⸻

Action Evidence

Verbs directly expressed by the user.

Examples

* Buy
* Sell
* Repair
* Replace
* Hire
* Learn

Important:

Only explicit actions become Action Evidence.

Implicit actions are inferred later.

⸻

Constraint Evidence

Hard requirements.

Examples

* Budget
* Deadline
* Maximum distance
* Minimum size

⸻

Preference Evidence

Soft requirements.

Examples

* Prefer Xiaomi
* Prefer owner
* Prefer female instructor

Failure to satisfy preferences does not invalidate the need.

⸻

Context Evidence

Background information.

Examples

* For my mother
* For my company
* Emergency
* Personal use

⸻

ADR-005

Evidence SHALL NOT contain business meaning.

Example

❌

category:
  gearbox_repair

Correct

object:
  gearbox
state:
  broken

Business interpretation belongs to the inference layer.

⸻

11. Evidence Graph

Evidence items never exist in isolation.

Relationships create meaning.

Example

Vehicle
     │
HAS_COMPONENT
     │
Gearbox
     │
HAS_STATE
     │
Broken

This graph still contains zero marketplace knowledge.

It only models reality.

⸻

12. Semantic Inference

Inference transforms evidence into meaning.

Example

Evidence

Vehicle
Gearbox
Broken
Replace

↓

Inference

intent:
  RequestService
service:
  GearboxReplacement

Notice:

Neither “RequestService” nor “GearboxReplacement” appeared in user input.

They are inferred.

⸻

ADR-006

Inference SHALL always preserve explainability.

Every inferred node MUST reference supporting evidence.

Example

Need:
RequestService
derived_from:
E2
E3
E4

This allows developers—and even users—to understand why the engine reached a conclusion.

⸻

13. Confidence Model

Confidence is assigned to evidence first, then propagated to inferred knowledge.

Example

Evidence
Vehicle
0.99
Gearbox
0.97
Broken
0.95
↓
Inference
Repair Service
0.94

Confidence decreases through inference unless additional supporting evidence is available.

⸻

ADR-007

Confidence SHALL propagate.

It SHALL never increase without new evidence.

This prevents artificial certainty.

⸻

14. Evidence Lifecycle

Evidence is immutable.

If the user corrects themselves, the engine does not modify existing evidence.

Instead, it appends new evidence.

Example

User

نه، منظورم تعمیر بود.

Previous

Replace

New Evidence

Repair

Inference is recomputed.

History remains intact.

⸻

ADR-008

Evidence SHALL be append-only.

Advantages

* Auditability
* Explainability
* Undo support
* Learning opportunities
* Analytics

⸻

15. Conflict Resolution

Conflicting evidence is expected.

Example

Message 1

فروش ماشین

Message 2

نه، قصد فروش ندارم.

Both remain in history.

Resolution selects the active interpretation.

The engine never destroys evidence.

⸻

16. Why Evidence First?

Evidence-first architecture separates AI from business logic.

The LLM extracts facts.

The platform derives meaning.

This separation improves:

* Determinism
* Testability
* Replaceability
* Explainability
* Future extensibility

⸻

Architecture Review

Alternative A — Direct Need Extraction

Text
 ↓
Need

Advantages

* Simpler implementation
* Lower initial complexity

Disadvantages

* Poor explainability
* Difficult debugging
* Model-dependent behavior
* Higher hallucination risk
* Hard to test

⸻

Alternative B — Evidence → Need (Selected)

Text
 ↓
Evidence
 ↓
Inference
 ↓
Need

Advantages

* Explainable
* Modular
* Easier testing
* Better confidence handling
* Easier to replace AI models
* Better support for future multimodal input (voice, image, documents)

Trade-offs

* Additional inference layer
* Slightly more implementation effort

⸻

Decision

Alternative B is adopted.

The Cognitive Engine SHALL treat evidence as the canonical semantic input to the reasoning pipeline.

Need representations SHALL always be derived from evidence.

Never directly extracted.

⸻

End of Part 2

RFC-002

Universal Need Representation Model (UNRM)

Part 3 — Need Inference Pipeline

Status: Draft

Version: 1.0

Depends On

* RFC-000
* RFC-001
* RFC-002 Part 1
* RFC-002 Part 2

⸻

17. Purpose

This section defines how the Cognitive Engine transforms evidence into a publishable Need.

The pipeline is deterministic.

The Large Language Model participates only in evidence extraction.

Inference belongs to the Cognitive Engine.

⸻

ADR-009

Decision

The Cognitive Engine SHALL separate extraction from inference.

LLMs extract.

The platform infers.

This separation guarantees explainability, deterministic behavior and model independence.

⸻

18. Cognitive Pipeline

The canonical pipeline is:

Natural Language
        │
        ▼
Normalization
        │
        ▼
Evidence Extraction
        │
        ▼
Evidence Validation
        │
        ▼
Evidence Graph
        │
        ▼
Need Inference
        │
        ▼
Need Validation
        │
        ▼
Clarification
        │
        ▼
Structured Need

Every stage has exactly one responsibility.

⸻

19. Pipeline Stages

Stage 1 — Normalization

Purpose:

Convert raw user input into normalized text.

Examples:

* Unicode normalization
* Persian character normalization
* Number normalization
* Emoji removal (when appropriate)
* Whitespace cleanup

No semantic interpretation occurs here.

⸻

Stage 2 — Evidence Extraction

Input

ماشینم گیربکسش خراب شده.

Output

Evidence
Vehicle
Gearbox
Broken

The engine extracts only directly observable facts.

⸻

Stage 3 — Evidence Validation

Every evidence item is checked.

Questions include:

* Is the value syntactically valid?
* Is the entity recognized?
* Does the evidence conflict with previous evidence?
* Is the confidence acceptable?

Invalid evidence is never discarded.

Instead it is marked for review.

⸻

Stage 4 — Evidence Graph Construction

Validated evidence becomes a semantic graph.

Example

Vehicle
   │
HAS_COMPONENT
   │
Gearbox
   │
HAS_STATE
   │
Broken

At this stage there is still no marketplace interpretation.

⸻

Stage 5 — Need Inference

This stage derives meaning.

Example

Evidence

Vehicle
Gearbox
Broken

↓

Possible Needs

* Repair Service
* Replacement Service
* Diagnostic Consultation

Multiple candidate needs may coexist.

Each candidate receives its own confidence score.

⸻

ADR-010

Inference SHALL produce candidates.

Never assume a single interpretation when evidence supports multiple possibilities.

⸻

Stage 6 — Need Validation

The Rule Engine evaluates inferred candidates.

Checks include:

* Marketplace support
* Policy constraints
* Required information
* Category availability
* Domain compatibility

Unsupported candidates are rejected.

⸻

Stage 7 — Clarification

Clarification is only triggered if required.

The engine SHALL ask questions only when:

* no valid candidate exists,
* two or more candidates have similar confidence,
* mandatory information is missing,
* publishing would otherwise be incorrect.

Otherwise, the pipeline proceeds directly to publication.

⸻

ADR-011

Clarification SHALL minimize user effort.

Every additional question must increase confidence or completeness.

Questions that do not materially improve the final Need MUST NOT be asked.

⸻

20. Candidate Ranking

Need candidates are ranked using a weighted score.

Conceptually:

Score =
Evidence Confidence
+
Ontology Match
+
Rule Consistency
+
Context Match
-
Conflict Penalty

The exact scoring algorithm is implementation-specific.

UNRM defines the concept, not the formula.

⸻

21. Determinism

Given:

* identical input,
* identical ontology,
* identical retrieval,
* identical rules,

the engine SHOULD produce the same Need.

Random behavior is undesirable.

⸻

ADR-012

Temperature-sensitive model behavior SHALL NOT determine business outcomes.

Business decisions belong to deterministic platform components.

⸻

22. Explainability

Every published Need must be explainable.

Example

Need
Vehicle Repair Service
Derived From
Vehicle
Gearbox
Broken
Confidence
0.96

The engine must always answer:

Why was this Need inferred?

⸻

23. Failure Modes

Inference may fail.

Common reasons:

* insufficient evidence,
* conflicting evidence,
* unsupported domain,
* unknown entities,
* low confidence.

Failure is an expected state.

The engine SHALL fail safely by requesting clarification rather than guessing.

⸻

Architecture Principles

The pipeline SHALL satisfy:

✔ Explainability

✔ Replaceable AI models

✔ Deterministic business logic

✔ Incremental inference

✔ Low hallucination risk

✔ Stateless LLM

✔ Stateful platform

⸻

Architecture Review

Alternative A

LLM directly generates final JSON.

Advantages

* Simple

Disadvantages

* Difficult to debug
* Difficult to test
* Difficult to explain
* Highly model-dependent

⸻

Alternative B (Selected)

LLM → Evidence → Inference → Need

Advantages

* Modular
* Explainable
* Easier testing
* Replaceable models
* Supports multiple AI providers
* Easier to optimize with local models such as Gemma

⸻

Decision

Alternative B is adopted.

The NiazFinder Cognitive Engine SHALL never rely on direct end-to-end LLM reasoning for business-critical decisions.

Business meaning is produced through deterministic inference over validated evidence.

⸻

End of Part 3

This section defines how the Cognitive Engine transforms extracted evidence into grounded knowledge using external structured data.

LLMs understand language.

Knowledge Bases understand reality.

The Cognitive Engine SHALL combine both.

⸻

ADR-013

Decision

The LLM SHALL never be considered the authoritative source of marketplace knowledge.

Instead,

all structured marketplace knowledge SHALL be resolved through dedicated knowledge services.

25. What is Grounding?

Grounding means replacing ambiguous language with verified marketplace entities.

Example

User

بنفشه

Gemma extracts

evidence:

        "بنفشه"

This is not a location.

It is only text.

district:
Benafshe
confidence:
0.97

Meaning is now attached to real data.

⸻

ADR-014

Raw text SHALL never become canonical knowledge.

Every entity must be grounded before entering the Universal Need Representation.

⸻

26. Resolver Layer

The Resolver Layer converts evidence into known marketplace entities.

Responsibilities

* Entity Resolution
* Synonym Resolution
* Location Resolution
* Category Resolution
* Brand Resolution
* Model Resolution

The resolver never performs AI reasoning.

It performs deterministic lookup.

⸻

27. Knowledge Sources

The architecture intentionally separates knowledge from intelligence.

Possible knowledge sources include:

* Elasticsearch
* PostgreSQL
* Synonym dictionaries
* Category indexes
* Location indexes
* Business taxonomies
* Brand registries

The Cognitive Engine does not depend on any single storage technology.

⸻

ADR-015

Knowledge SHALL be technology independent.

Replacing Elasticsearch with another search engine SHALL NOT change the Cognitive Model.

30. Multi Candidate Strategy

Every resolver returns ranked candidates.

Never one result.

Why?

Because ambiguity is normal.

Example

31. Knowledge Independence

The Cognitive Engine SHALL operate even when knowledge services are unavailable.

In this case

Evidence remains unresolved.

Need inference proceeds with reduced confidence.

The platform degrades gracefully.

ADR-017

It SHALL NOT stop the pipeline.

Caching is an optimization.

Part 5 — Cognitive Decision Engine (CDE)

⸻

34. Purpose

The Cognitive Decision Engine (CDE) is responsible for transforming multiple candidate interpretations into a single publishable representation.

The CDE SHALL never rely on a single source of truth.

Instead, every decision is based on accumulated evidence.

⸻

ADR-018

Decision

The Large Language Model SHALL NOT make final marketplace decisions.

Its responsibility ends after evidence extraction.

Business decisions belong to deterministic platform components.

⸻

35. Why a Decision Engine?

Consider the sentence:

ماشینم روشن نمی‌شود.

Evidence

Object:
Vehicle
State:
Not Starting

Knowledge Layer returns

Candidates
Battery Problem
Starter Motor
Fuel System
Tow Truck
Mechanic
Car Sale

Who decides?

Not Gemma.

Not Elasticsearch.

Not PostgreSQL.

The platform decides.

⸻

36. Candidate

Every candidate is a hypothesis.

Example

Candidate A
Repair Service
Confidence
0.82
Candidate B
Tow Truck
Confidence
0.67
Candidate C
Battery Replacement
Confidence
0.64

Candidates compete.

Not overwrite.

⸻

ADR-019

The engine SHALL preserve multiple hypotheses until sufficient evidence exists.

Premature certainty is considered an architectural defect.

⸻

37. Decision Inputs

Every decision is computed using multiple independent signals.

Signals include:

Evidence Quality

Knowledge Match

Ontology Match

Historical Context

Conversation State

Business Rules

User Corrections

Missing Information

No single signal is authoritative.

⸻

38. Decision Score

The specification intentionally does not define a mathematical formula.

Instead,

every implementation SHALL satisfy these properties:

Higher evidence quality increases score.

Conflicts decrease score.

Resolved entities increase score.

User confirmation overrides inference.

Business rules may invalidate a candidate regardless of score.

⸻

ADR-020

Platform policies always have higher priority than statistical inference.

⸻

39. Decision States

A candidate may exist in one of five states.

↓

↓
Confirmed
↓

Generated

Created from evidence.

Supported

Validated by knowledge.

Preferred

Highest current score.

Confirmed

Verified by user or deterministic rules.

Published

Accepted by marketplace.

⸻

Notice

The platform may stop at any stage.

It never needs to reach Published automatically.

* Publish directly from raw LLM output.

Part 13 — Reference Implementation Notes (Non-Normative)

Status: Informative

Version: 1.0

Added: 2026-07-07, during Phase 1 implementation planning.

⸻

123. Purpose

Parts 1–12 intentionally leave several choices open (§38 decision-score formula, §68
serialization format, and all of performance/scale/migration — deliberately deferred to future
RFCs per the design review after Part 11).

This Part is NOT normative. It does not change UNRM. It records the concrete choices made for the
first reference implementation inside the existing NiazFinder codebase, so future readers don't
have to re-derive them from commit history. A different implementation may choose differently and
still conform, as long as it satisfies the Part 12 checklist.

⸻

124. Serialization

TypeScript interfaces under `src/cognitive-engine/types/`, one file per concept (`evidence.ts`,
`claim.ts`, `diagnostics.ts`), each with a companion Zod schema for runtime validation. Zod schemas
run at exactly two boundaries: when Evidence returns from the LLM adapter (§105 Adapter Layer), and
when a Canonical Need Object is about to be persisted (publish boundary). Internal passes between
those two points trust the TypeScript types without re-validating.

⸻

125. Decision Score Formula (v1, revised during Phase 3 implementation)

Per §38, the specification intentionally does not fix a formula, only properties the formula must
satisfy. The original draft of this section proposed a four-term weighted sum
(evidenceConfidence/ontologyMatch/ruleConsistency/contextMatch). Building Phase 3's Cognitive
Decision Engine surfaced two problems with implementing that formula literally, before any of the
other three terms have a real subsystem behind them:

* Filling `ontologyMatch`/`ruleConsistency`/`contextMatch` with a placeholder constant would give
  every candidate the same unearned 60% of its score, diluting the one term that's actually
  computed from real signal (`evidenceConfidence`).
* A naive per-candidate conflict penalty (subtracting it only from the top-ranked candidate) can
  invert the ranking when the penalty exceeds the raw confidence gap — a narrowly-second-place
  candidate ending up with a higher final score than the leader. Caught by Phase 3's self-test, not
  by inspection.

Revised v1, implemented in `src/cognitive-engine/decision/decision-engine.ts`:

```
conflictPenalty = clamp01(0.15 - (topConfidence - runnerUpConfidence))   // one scalar per decision
score           = clamp01(candidateConfidence * (1 - conflictPenalty))  // applied to every candidate
```

Applying the same `conflictPenalty` multiplicatively to every candidate (not just the leader)
preserves relative order by construction, while still satisfying §38's "conflicts decrease score."
`ontologyMatch`/`ruleConsistency`/`contextMatch` are deferred entirely — not included, not
faked — until Phases 4-6 build ontology versioning, cross-field rule checks, and Cognitive
State/context, at which point they should be added to `ScoreBreakdown` as terms backed by real
computation, and this section should be revised again.

Tunable via Learning Signals (Part 6) without requiring an RFC change — the weights are
implementation detail, not specification.

⸻

126. Migration & Rollout Strategy

Not addressed anywhere in Parts 1–12, because RFC-002 describes *what* a Need is, not *how to
safely get there* in a system that already has a production intake engine serving real users.

For the NiazFinder reference implementation specifically: the Cognitive Engine SHALL be built as an
additive, shadow-mode system living alongside the existing `src/intake/intelligence-engine/` hybrid
pipeline. No phase of implementation changes the behavior of a live request until:

1. A shadow/parity self-test exists comparing new output to the existing pipeline's output on the
   same fixture inputs, and passes.
2. The responsible engineer explicitly approves cutover for that phase.

A feature flag (`NEED_INTAKE_COGNITIVE_ENGINE_ENABLED`) gates the eventual live cutover, with the
existing pipeline retained as instant rollback for at least one release cycle after cutover.

⸻

127. Storage for Evidence, Claims & Cognitive State (Part 9)

Per §Architecture Principles of Part 9, the specification deliberately does not pick a storage
technology. Reference choice for NiazFinder:

* **Need Scope** (permanent, auditable — Evidence and Claims once a Need exists): new Prisma
  tables, additive migrations only, never altering existing `ServiceRequest`/`NeedIntakeSession`
  columns.
* **Interaction Scope** (ephemeral, ADR-039/§88 State Recovery): rebuilt from persisted Evidence if
  lost, cached in-memory or Redis (already in the stack via docker-compose) for latency.

⸻

128. Existing-Code Mapping (informative)

The first implementation phase found that much of the conceptual architecture in Parts 2–11 already
exists informally in `src/intake/intelligence-engine/` (rule-first resolvers that retrieve without
deciding, an OpenAI-compatible provider-agnostic chat adapter, a truth-verifier with
confidence-and-lock-aware override logic, ranked category/city candidates). The reference
implementation's phasing therefore prioritizes *formalizing and wrapping* that existing, proven code
over rewriting it — new code under `src/cognitive-engine/` is additive and calls into the existing
modules rather than duplicating their logic. This is a reference-implementation observation, not a
requirement Part 12 conformance depends on.

⸻

129. AI Boundary: Existing Legacy Call Sites vs. the Cognitive Contract (Phase 6)

RFC-002 Part 11 defines the Cognitive Contract every AI adapter must satisfy (Evidence +
Diagnostics, §104, implemented in `src/cognitive-engine/types/cognitive-contract.ts`). The
reference implementation's original Phase 6 plan called for retrofitting this contract onto
~7-8 existing production AI call sites. Building it revealed that would contradict the additive,
shadow-mode principle every phase has followed since Phase 1 (never modify a file the live
`/post` request path depends on). Auditing those call sites against Part 11 instead:

* **Already conforms in spirit**: `src/lib/need-intake/local-chat-client.ts`. It's a genuine
  provider-agnostic OpenAI-compatible client — retries, timeouts, and JSON-extraction are already
  standardized, and swapping the underlying model (Gemmafable → Gemma 3n E4B, done earlier this
  project) required zero caller changes. Phase 1's adapter reuses this file unchanged rather than
  replacing it.
* **Legacy pattern the Decision Engine is meant to replace, not wrap**: `category-disambiguation.ts`
  and `city-disambiguation.ts`'s "ask the LLM to pick one slug from a list" pattern is in tension
  with ADR-018 ("the LLM SHALL NOT make final marketplace decisions") — it treats the model's pick
  as close to authoritative, only lightly revalidated. Phase 3's Decision Engine already provides
  the RFC-conformant alternative (deterministic scoring over grounded candidates, no AI vote).
  Wrapping the legacy pattern in the new contract would formalize something the architecture is
  meant to move away from; migrating live category/city selection onto the Decision Engine is a
  cutover-phase decision (Phase 7), not a Phase 6 wrapping exercise.
* **Out of scope entirely**: `local-copy-bridge.ts`'s title/listing-copy generation. RFC-002 is
  about representing a Need, not generating marketing copy for a published listing — this is a
  downstream, post-Readiness concern outside the UNRM's scope by the RFC's own Non-Goals (RFC-000:
  "the Cognitive Engine is not... business logic").
* **Deferred, not ignored**: `truth-verifier.ts`. A genuinely complex, already-AI-driven
  verification subsystem already live in production. A shallow wrapper without first deeply
  understanding its existing verdict/override behavior risked degrading something proven. Phase
  4's Claims already carry everything Part 8 needs (confidence + evidence provenance) without it;
  real integration is deferred until there's a concrete reason to reconcile the two.

Conclusion: Phase 6 formalizes the *contract* (Cognitive Contract type, a mock adapter satisfying
§111's testing-without-AI requirement, and the composed reference pipeline of §114) rather than
retrofitting unrelated production files. This satisfies Part 12's conformance checklist (verified
in `run-conformance-self-test.ts`) without touching anything the live `/post` route depends on.
