# ثبت نیاز طبیعی در `/post`

## معماری

دکمهٔ «تکمیل هوشمند فرم» تنها نقطهٔ شروع تحلیل است؛ تایپ کاربر inference اجرا
نمی‌کند و هیچ ثبت خودکاری انجام نمی‌شود.

```text
textarea
  -> /api/post/natural-analyze
     -> نرمال‌سازی فارسی و parser قطعی
     -> باریک‌کردن گزینه‌های شهر/محله و دسته
     -> worker خصوصی Si
     -> merge با اولویت مقدار دستی کاربر
     -> patch قابل ویرایش روی draft فرم
```

route انتشار همچنان از validation و جریان فعلی `/post` استفاده می‌کند. نتیجهٔ
تحلیل طبیعی یک پیشنهاد/patch است و به‌تنهایی post ایجاد نمی‌کند.

## مدل و اجرای محلی

تنها checkpoint این قابلیت `convaiinnovations/si-multilingual` است. اتصال از
API مستقیم `si.load()` و یک `Agent.predict(state, questions)` انجام می‌شود؛
Router استفاده نمی‌شود و متن کاربر به endpoint inference ابری ارسال نمی‌شود.

منبع رسمی Si: [repository رسمی](https://github.com/NandhaKishorM/si) و
[checkpoint رسمی](https://huggingface.co/convaiinnovations/si-multilingual).

نسخهٔ Python package برابر `si==0.3.20` است و Python 3.10 یا جدیدتر لازم
دارد. مدل در startup worker یک بار load می‌شود و بین requestها reuse می‌شود:

```bash
npm run setup:si-post
npm run dev:si-post
npm run smoke:si-post
```

worker فقط روی `127.0.0.1:8101` گوش می‌دهد. cache از `SI_CACHE_DIR` (و در
صورت تنظیم، `HF_HOME`) خوانده می‌شود؛ اگر خالی باشد cache استاندارد Hub استفاده
می‌شود. `SI_DEVICE` یکی از `auto`, `mps`, `cuda`, `cpu` است.

اگر محیط Python یا مدل آماده نباشد، `/health` وضعیت `model_loaded: false` می‌دهد
و API وب با patch قطعی و فرم دستی ادامه می‌دهد.

## تقسیم fieldها

parser قطعی مسئول اعداد، واحدها، متراژ، بازهٔ متراژ، خواب، بودجه، رهن، اجاره،
تبدیل رقم‌های فارسی/عربی و تطبیق مکانی است. برای شهر، route تحلیل از نام‌های
کاتالوگ کامل مکان‌ها استفاده می‌کند (نه فقط رجیستری کوچک URL)؛ trie یک‌بار و
به‌صورت lazy ساخته می‌شود. شهر انتخاب‌شدهٔ کاربر مرجع باقی می‌ماند؛ نام‌های
تکراری بین چند شهر بدون زمینهٔ کافی مبهم می‌مانند. محله فقط در کاتالوگ همان شهر
جست‌وجو می‌شود و در صورت تطبیق، شناسه و centroid محله به فرم/نقشه می‌رسد؛ مرکز
شهر جایگزین محله نمی‌شود. تطبیق نزدیک و چندگزینه‌ای فقط پیشنهاد است.

در rent، مبلغ رهن و
اجاره در slotهای جدا می‌مانند و به `budgetMax` تبدیل نمی‌شوند.

Si فقط روی decisionهای typed و محدود کار می‌کند:

- `transaction_type`
- `property_kind`
- `deed_type`
- `usage`
- `parking`, `elevator`, `storage` با سه وضعیت yes/no/unknown
- `category_candidate` فقط وقتی shortlist محدود و واقعاً مبهم وجود دارد

ریشه‌ای مثل `services` به اولین فرزند تبدیل نمی‌شود. category پیشنهادی قفل
نیست؛ انتخاب مستقیم کاربر قفل ایجاد می‌کند. شهر انتخاب‌شدهٔ کاربر نیز قابل
overwrite نیست. `SI_POST_AUTO_APPLY` پیش‌فرض `false` دارد؛ تصمیم‌های
categorical مدل تا تأیید کاربر proposal می‌مانند و parser قطعی اولویت دارد.

وقتی متن محله دارد ولی هیچ شهری در متن/فرم/قفل/URL نیست، route از ایندکس
exact سراسری نام محله (نام‌ها و areaهای هر ۱٬۲۰۷ کاتالوگ، lazy و کش‌شده)
استفاده می‌کند — نه از امتیاز فازی کل متن (که مثلاً «۱۳۰ متری» را با خیابان
«۳۰ متری» اهواز اشتباه می‌گرفت و شهر غلط می‌گذاشت):

- تطبیق دقیق در دقیقاً یک شهر ⇒ شهر خودکار (confidence ‏0.9، evidence فارسی،
  قابل تغییر) و سپس resolve شهر-scoped همان شهر برای محله + centroid.
- تطبیق در چند شهر ⇒ هیچ شهری حدس زده نمی‌شود؛ کاندیداها (حداکثر ۴، رتبه‌بندی
  با اولویت شهرهای بزرگ، هر کدام با نام شهر و شناسهٔ کاتالوگ شهر) در
  `locationCandidates` برمی‌گردند. تحلیل Path A هنگام رفتن به مرحلهٔ location
  هم خودکار اجرا می‌شود: مورد یکتا همان‌جا پر می‌شود، و مورد چندشهری به چیپ
  «شهر: …» در «پیشنهادهای مکان» تبدیل می‌شود؛ با انتخاب شهر، محله در همان شهر
  خودکار resolve می‌شود. سؤال محلهٔ Si بدون شهر ساخته نمی‌شود.
- بدون تطبیق ⇒ رفتار قبلی (fallback فازی + فرم دستی).

## تست و benchmark

مجموعهٔ فعلی ۵۴ نیاز فارسی واقعی‌نما دارد و شامل اعداد دو script، محاوره، typo،
عدم ذکر field، مقدار منفی، بازه و مسیرهای ملکی/خدماتی است:

```bash
npm run test:post-natural
```

benchmark پیش‌فرض rules-only است تا معیار parser با نتیجهٔ model-backed قاطی
نشود. خروجی accuracy، false positive و false negative هر field را چاپ می‌کند؛
وقتی worker با checkpoint آماده باشد، smoke جداگانهٔ آن با
`npm run smoke:si-post` و benchmark مدل با `npm run benchmark:si-post`
انجام می‌شود. benchmark مدل روی همین ۵۴ نمونهٔ فارسی اجرا شده و خروجی آن باید
قبل از هر فعال‌سازی auto-apply بررسی شود.

آخرین اجرای محلی: ۵۴/۵۴ درخواست Si موفق، دستگاه `mps`، میانگین latency خود
worker برابر ۲۵۹ میلی‌ثانیه و زمان کل ۱۴٫۷ ثانیه بود. دقت خام تصمیم‌های
categorical هنوز برای auto-apply کافی نیست؛ به همین دلیل خروجی مدل در حالت
پیش‌فرض فقط proposal است و parser قطعی مرجع فیلدهای exact باقی می‌ماند.

در سخت‌سازی مکانِ ۲۰۲۶-۰۹-۲۶، تطبیق نام دقیق برای هر ۱٬۲۰۷ کاتالوگ شهر با
شناسهٔ خودش بررسی شد (۱٬۲۰۷/۱٬۲۰۷). ۲۴ برچسب نام شهر در چند کاتالوگ تکرار
می‌شوند؛ بدون شهر انتخاب‌شده یا راه رفع ابهام معتبر، سیستم عمداً حدس نمی‌زند.
تست route سناریوهای شهر قفل‌شدهٔ مشهد + «فرامرزعباسی»، تهران + «ونک»، شهر
کاتالوگی «اندیشه»، استنتاج خودکار شهر یکتا از «جردن» (تهران + centroid) و
چندشهری «نیاوران» (بدون حدس شهر، کاندیداهای شهر‌دار، بدون سؤال Si) را پوشش
می‌دهد؛ مورد ونک centroid محله را بررسی می‌کند.

## امنیت و محدودیت

API وب payload را محدود و rate-limit می‌کند، schema را قبل از merge بررسی می‌کند،
requestهای قدیمی در client با abort/request id کنار گذاشته می‌شوند، و worker
متن خام کاربر را log نمی‌کند. کم‌اعتمادی Si فقط proposal می‌سازد؛ fallback آن
فرم دستی و rules-only است.

cache واقعی checkpoint در این محیط حدود ۱٫۳ گیگابایت است. physical footprint
worker روی MPS پس از warm شدن حدود ۲٫۷ گیگابایت اندازه‌گیری شد؛ RSS سادهٔ
پردازه این حافظهٔ GPU/Metal را کامل نشان نمی‌دهد. route در پاسخ latency تحلیل
rules و worker را جداگانه نگه می‌دارد؛ یک درخواست گرم end-to-end در این محیط
حدود ۱٫۲ ثانیه بود.
